## Objective

Create `projects/<project-slug>/planning/implementation-catalogue-index.md` and
`implementation-catalogue-index.json` from the canonical specification.
Decompose the first bounded domain chapter (at most 250 implementation
contracts) into atomic implementation contracts,
using stable IDs such as `IMP-0001`, and create a domain-expansion queue for
the remaining chapters. Do not write the final R-series runbooks yet.

An implementation contract is the smallest independently verifiable slice that
can be safely handed to an implementation agent. It may be code, content,
configuration, research with an explicit output, test automation, migration,
documentation, build/release work, or platform certification work.

Derive contracts from the complete domain specification, including product
content, tooling, operations, and quality work as first-class implementation
work where relevant. An RPG might yield story, character, quest, combat,
balancing, localisation, and content-tool contracts; an IDE might yield parser,
language-service, debugger, extension-host, workspace, and source-control
contracts; an operating system might yield kernel, driver, identity, process,
storage, installer, and system-settings contracts. The mechanism must derive,
not assume, the appropriate set for any product.

For every game, create a machine-readable `game_coverage` map. Every `GAME-*`
design unit from the game identity and design bible maps to a current or named
queued `IMP-*` contract. Contracts must cover the selected design module's
rules, content/design-card production, validation/provenance, runtime
integration, and verification where those are distinct. A generic state
machine, schema, or documentation contract does not by itself cover a promised
player-facing game system. When the narrative module is selected, also create
`narrative_coverage` for the `NAR-*` story/content units.

The coverage map must also preserve each design unit's selected module and its
production-inventory entries. It is invalid for a selected module to be covered
only by a generic framework, state machine, or data schema: its player-facing
rules, actual finite content or bounded catalogue batches, content validation,
runtime integration, and verification need owned routes. This is how an RPG's
named world/party/boss/quest work and a football trivia game's actual question
catalogue/fairness/adjudication work remain different through decomposition.

When `04-asset-direction.md` exists, include visual asset planning, original
asset generation or sourcing, integration, provenance, accessibility, and QA as
first-class contracts with explicit ownership and dependencies; do not bury
them in generic UI or content work. When `04-audio-direction.md` exists,
include audio direction, cue implementation, local generation, integration,
mixing, accessibility, and QA as first-class contracts with explicit ownership
and dependencies; do not bury them in UI work. The first relevant asset/audio
contract may establish shared manifests and integration seams, but every asset
family and cue-map entry must be allocated to one or more later contracts.

Create a machine-readable `asset_audio_coverage` map in the catalogue. It must
list every exact family ID and cue ID declared by the canonical direction files,
its owning (or explicitly queued) `IMP-*` ID, the named expansion shard when it
is queued, and the intended contract kind: direction/integration, generation,
or QA. Do not collapse a whole game's presentation into one generic asset
record: separate contracts are required where ownership, creation method,
runtime trigger, verification, or dependency differs. A simple game still
needs enough bounded work to create and integrate its original screens, world,
characters, UI, feedback, music, and sound effects when those are declared.
For a non-game product, apply the same rule to whatever visual or audio
families its specification actually requires; do not invent media for a
text-only or explicitly silent product.

The initial shard may be foundations, but the expansion queue must contain a
named presentation/content-assets shard whenever visual or audio direction
exists. That shard must be eligible before a final audit. It owns asset/cue
manifest seams plus the individual generation, integration, accessibility, and
QA work; it is not satisfied by a schema-only content contract.

The canonical machine-readable field is `creative_coverage`, with `game`,
`assets`, `audio`, and (when present) `narrative` maps. Each exact `GAME-*`,
`ASSET-*`, `AUDIO-*`, or `NAR-*` ID maps to an object containing `imp_ids`, `shard` (`current` or a
named expansion shard), and one or more `roles` from `generation`,
`integration`, `provenance`, `accessibility`, or `qa`. Every referenced IMP
record repeats the ID in `creative_coverage_ids`. This is deliberately
redundant so `scripts/runbookgen validate <project>` can reject omissions
without asking an LLM to interpret prose.

## Acceptance criteria

- Every record includes title, domain, target(s), requirement IDs, bounded
  outcome, prerequisites, files/data/API ownership, forbidden scope,
  verification, human/external gate, and estimated authoring complexity.
- The index covers foundation, data, domain logic, UI/UX, content, input,
  accessibility, security, privacy, performance, observability, tests,
  operations, documentation, delivery, and platform-specific work when in
  scope. Each expansion task adds at most 250 contracts in one bounded domain
  shard rather than making an
  unbounded one-shot request.
- Dependencies form an acyclic graph; cross-cutting prerequisites are explicit
  and no task has ambiguous ownership.
- The catalogue distinguishes shared work from each platform adapter and avoids
  a false assumption that every target has the same UI or delivery path.
- The index reports every `REQ-*`/`NFR-*` as covered by a current contract,
  queued for a named domain expansion, intentionally deferred, gated, or
  rejected with a recorded reason.
- When an asset or audio direction exists, the index maps every required asset
  family and cue-map entry to a current or queued `IMP-*` contract. A game
  cannot claim a complete implementation catalogue while its declared art,
  music, sound-effect, or other required asset work has no owned contract.
- The `asset_audio_coverage` map contains every canonical family/cue ID,
  exactly one owning or named queued `IMP-*` contract, its creation/
  integration/QA route, and a named eligible shard. A generic content-schema
  contract alone is not valid coverage for a declared visual or audio family.
- For a narrative/content model, `narrative_coverage` maps every first-release
  content family to a current or named queued implementation contract with
  creation, validation/provenance, runtime integration, and QA routes. A game
  cannot claim a complete first-release plan while its promised story is only a
  schema or an unallocated future idea.
- Every game-design-bible `GAME-*` unit appears in `creative_coverage.game`
  and is mapped to an owned current or queued IMP route. A game cannot claim
  completeness while a selected genre module or its required design-card
  production is merely described in prose.
- `game_coverage` identifies the selected module and production-inventory IDs
  for every `GAME-*` unit. Every selected module has a player-facing and a
  production/validation route; neither an RPG nor a trivia game can pass using
  a generic “content system” as its only allocation.
