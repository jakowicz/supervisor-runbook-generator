## Objective

Generate only the bootstrap wave of ordinary Supervisor runbooks in
`projects/<project-slug>/authoring-runbooks/`: a bounded catalogue-expansion
task followed by a dispatcher task. The dispatcher allocates at most ten
authoring B-series tasks per wave, creates one successor dispatcher, and stops.
Each authoring task instructs Codex to create only its assigned R-series
implementation runbooks under
`projects/<project-slug>/runbooks/`, then validate their metadata and update the
manifest. The successor dispatcher repeats this process until no queued
catalogue chapter or unassigned implementation contract remains. Generate an
`INITIAL.md` context document in `authoring-runbooks/`
that points to the canonical `PROJECT_BRIEF.md` and specification.

Register the generated authoring collection with the source collection by
writing `runbooks/.supervisor-children/<project-slug>.json` containing
`{"runbooks_dir": "../projects/<project-slug>/authoring-runbooks"}`. Also
write `authoring-runbooks/.supervisor-children/implementation.json` containing
`{"runbooks_dir": "../runbooks"}`. These are explicit child-collection
registrations; `supervisor-run --run-all` follows them automatically after the
parent collection is accepted.

Every dispatcher first expands at most one queued specification/catalogue domain
chapter (maximum 250 `IMP-*` contracts), validates its coverage, then allocates
ready contracts. If any queued chapter or ready contract remains, it creates no
more than ten authoring tasks and exactly one successor dispatcher. If none
remains, it creates the final audit task instead. This is a durable loop, not a
recursive prompt or an unbounded single run.

Every generated R-series runbook must use the standard Supervisor front matter
and contain: precise objective; dependencies; relevant requirement IDs; owned
files/data/interfaces; required behaviour; non-goals; platform differences;
verification commands/evidence; and observable acceptance criteria. It must be
small enough for one implementation task, not a vague epic.

Every generated R-series runbook must retain machine-readable provenance to the
canonical decisions that justify it. Its front matter must declare all of these
non-empty fields, using comma-separated values where more than one applies:

```yaml
source_specifications: specification/03-technical-contract.md#save-state
source_catalogue_ids: IMP-SAVE-001
authoring_batch: B0007
factory_stages: F003,F005,F012,F013
```

`source_specifications` points to the smallest relevant canonical
specification section; `source_catalogue_ids` identifies the allocated
implementation-catalogue records; `authoring_batch` identifies the B-series
writer that created the R file; and `factory_stages` identifies the F-series
stages that established the requirement. This is a traceability trail, not an
instruction to inject every F or B runbook into the implementation agent's
prompt. The R task uses these links to read only the canonical context it needs.

Every generated R-series runbook must also include a detailed asset assessment.
Its front matter must always declare both fields below, even when no assets are
needed:

```yaml
asset_impact: required # or not_applicable
asset_ids: village_gate_main,village_gate_construction # blank only when not_applicable
```

For `asset_impact: required`, the B-series writer must reserve stable,
product-specific asset IDs (never generic names such as `image1`), provide an
`asset_brief` and `visual_style_version`, and include an `## Asset assessment`
section explaining the assets' purpose, where they appear, the required visual
states/variants, source-of-truth ownership, and original-art acceptance checks.
For `not_applicable`, that section must explain why the scope needs no generated
or source visual asset and explicitly prohibit incidental asset creation. This
keeps UI, illustration, icon, texture, sprite, audio-visual, and other product
asset work visible in the implementation plan instead of discovering it midway
through coding.

Each B-series authoring task may create at most seven R-series implementation
runbooks. It must stop after its assigned seven (or fewer), update the manifest,
and leave remaining work for the next bounded batch.

## Acceptance criteria

- The initial collection contains only a bounded bootstrap wave; each
  dispatcher expands at most one 250-contract domain shard, creates at most ten
  new B-series authoring tasks plus one successor, then exits. It never attempts
  to materialise the whole game plan.
- There is exactly one valid B-series authoring runbook per allocated manifest
  batch, and it creates no more than seven assigned R-series runbooks.
- B-series runbooks never overwrite an existing R-series contract with a
  conflicting ID; they stop and report mismatches.
- Every generated B-series runbook includes its context packet, output list,
  validation procedure, checkpoint/update procedure, and a clear stop condition.
- Both child-collection registration files exist, contain valid JSON with a
  relative `runbooks_dir`, and point to the generated authoring and
  implementation collections respectively.
- R-series contracts use stable IDs and parse with the Supervisor runbook
  loader; their declared dependencies match the manifest, every contract has
  explicit `asset_impact` and `asset_ids` metadata, and asset-required
  contracts have non-empty stable IDs. Every R contract also has non-empty,
  valid `source_specifications`, `source_catalogue_ids`, `authoring_batch`,
  and `factory_stages` provenance metadata.
- The collection contains a final audit B-series task after all authoring
  batches and catalogue expansions are complete, rather than pretending that
  thousands of contracts can be reviewed in one generation step.
