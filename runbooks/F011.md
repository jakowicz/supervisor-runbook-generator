## Objective

Use F001–F010 to create the canonical specification beneath
`projects/<project-slug>/specification/`. Consolidate the brief, feature,
technical, experience, and delivery documents into a coherent set of documents
that any later author can use without rediscovering scope. Assign stable IDs
such as `REQ-0001`, `NFR-0001`, `DEC-0001`, `RISK-0001`, and `GATE-0001`.

This must work for a game, app, operating-system component, document set,
service, desktop product, TV product, or any other selected product category.
Model target-neutral requirements separately from target-specific adaptations.
For a large product, create a specification index plus bounded domain chapters
(for example combat, quests, progression, social, economy, tools, or platform
delivery), rather than requiring one document to contain every detail.

The canonical specification must prove that it understood what kind of product
it is building. It must convert the discovery map into an appropriate complete
domain specification before work is decomposed. For example, this may be an
original story/world/character and game-rules bible for an RPG, a language and
extension platform specification for an IDE, or a system-service and security
model for an operating system. No category is privileged; use the disciplines
discovered from the brief.

## Acceptance criteria

- `requirements.md` and `requirements.json` list every functional, quality,
  accessibility, privacy, platform, release, and content requirement with ID,
  priority, source, rationale, target applicability, verification method, and
  status.
- A traceability matrix maps every requirement to journeys, components,
  implementation-contract IDs, implementation runbook IDs when assigned, and
  final evidence.
- A decision log records owner, due point, alternatives, default behaviour, and
  consequence for every unresolved decision; no decision is silently invented.
- A platform appendix records each selected platform's input, capability,
  policy, distribution, accessibility, performance, and parity differences.
- The specification index records chapter IDs, ownership, dependencies, and
  completion state so later tasks can expand it in small, resumable waves.
- A domain-completeness review explicitly checks every discovered system family
  has a requirements chapter, entities/rules, cross-domain dependencies,
  authoring model where needed, and a release-scope decision.
- Original-design and reference boundaries remain explicit in every document.
