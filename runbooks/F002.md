## Objective

Use F001 to create `projects/<project-slug>/specification/02-feature-model.md`: personas, jobs,
core journeys, domain vocabulary, entity lifecycles, and a prioritised feature
catalogue with first-release, later, and deferred slices. Model the selected
product category and targets; do not assume every project is a game, mobile app,
or web application.

Expand every accepted system family from `00-domain-discovery.md` into a
domain chapter and an explicit system relationship map. Cover product content,
user workflows, rules, data, services, tools, quality attributes, operations,
and platform concerns wherever the discovery map requires them. For example,
an RPG needs creative and gameplay chapters; an IDE needs editing, language,
debugging, extension, and workspace chapters; an operating system needs system,
hardware, security, installation, and management chapters. The exact chapters
must arise from the brief, not any example list.

For every game, and for a narrative-led non-game product, create
`specification/02-narrative-content-model.md` alongside the feature model.
Turn the early creative direction into implementable, original content
requirements: story premise and first-release arc; playable role; world and
location model; character/relationship roles; quest, scene, dialogue, tutorial,
encounter, reward, and ending structures; player choices and state; content
authoring workflow; localisation/caption needs; continuity rules; and the
minimum original content needed for a complete first useful session. Link each
story/content element to the gameplay or product journey it supports. This is
not permission to write a vast game script in one step: define bounded content
packages and scalable authoring units. A game may use a lightweight
presentation/goal model instead of a long-form plot, but it still records this
content model. A non-narrative non-game product creates an explicit
content/communication model appropriate to it instead.

Every game content unit in this file uses a stable `NAR-*` ID (for example
`NAR-PREMISE`, `NAR-PLAYER-GOAL`, `NAR-LOCATION-HUB`, or `NAR-END-01`). These
IDs are planning/provenance identifiers, not a requirement to write a full
script. They let later implementation, asset, audio, and localisation work
prove that every promised player-facing content unit has an owner.

## Acceptance criteria

- Every feature maps to a user outcome and journey.
- Normal, empty, invalid, permission-denied, offline, conflict, recovery, and deletion paths are specified where relevant.
- The first release provides one complete useful journey without deferred dependencies.
- Cross-target capability parity and intentional target-specific differences are documented.
- Each domain chapter defines its entities, rules, lifecycle, authoring inputs,
  dependencies, player/user outcomes, edge cases, and first-release boundary.
- The relationship map identifies cross-domain invariants and lifecycle
  boundaries. For example, an RPG quest links narrative and save state; an IDE
  edit links language analysis, workspace indexing, and version control; an OS
  permission links identity, process, storage, and user settings.
- Every game and narrative-led product has a narrative/content model that maps premise, player
  role, setting, characters, content units, progression, choice/consequence,
  ending, localisation/accessibility, and originality boundaries to first
  release journeys and implementation domains.
