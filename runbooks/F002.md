## Objective

Use F001 to create `projects/<project-slug>/specification/02-feature-model.md`: personas, jobs,
core journeys, domain vocabulary, entity lifecycles, and a prioritised feature
catalogue with first-release, later, and deferred slices. Model the selected
product category and targets; do not assume every project is a game, mobile app,
or web application.

Expand every accepted system family from `00-domain-discovery.md` into a
domain chapter and an explicit system relationship map. Cover product content,
user workflows, rules, data, services, tools, quality attributes, operations,
and platform concerns wherever the discovery map requires them. For example,
an RPG needs creative and gameplay chapters; an IDE needs editing, language,
debugging, extension, and workspace chapters; an operating system needs system,
hardware, security, installation, and management chapters. The exact chapters
must arise from the brief, not any example list.

For every game, create `specification/02-game-design-bible.md` and
`02-game-design-bible.json` alongside the feature model. Start from the common
game identity and its game-design signals, then select only the genre modules
the game needs. The JSON records `game_archetypes`, `selected_modules`,
`rejected_modules`, and `design_units`. Every design unit has a stable
`GAME-*` ID, module, player outcome, source evidence, first-release boundary,
dependencies, and production mode (`finite_named_content`, `bounded_content_set`,
`systemic_rules`, or `scalable_catalogue`). Possible modules include narrative/world,
characters/factions, quests/scenes/dialogue, combat/encounters/bosses,
classes/abilities/status effects, units/buildings/resources, economy,
progression/balance, levels/maps, puzzles, racing/sport rules, multiplayer,
social/safety, live content, and tooling. These are a menu, not a checklist.

Each selected module becomes an implementable design system: define the
entities, player-facing rules, content packages, authoring workflow, quantities
or scope boundaries, dependencies, visual families, audio cues, accessibility,
and testable acceptance. An FF-style RPG therefore selects story, party,
world, quests, combat, jobs/abilities, enemies/bosses, progression, locations,
and content production; a Clash-style builder selects base, resources,
buildings, troops, battles, progression, economy, and social/safety instead.
Narrative is a selected module when the game needs structured story content;
then create `02-narrative-content-model.md` using `NAR-*` IDs. Do not create a
long script in one step: create bounded content packages and scalable design
cards that later R runbooks can own.

Do the same depth of design for every archetype, without copying any reference
product. For a football trivia game, the bible should instead determine its
question-source/provenance rules, football eras/leagues/categories, question
types, answer-normalisation and adjudication, difficulty and fairness model,
round and mode rules, scoring/timer/streak logic, anti-repeat policy, content
quantities, editorial/validation workflow, accessibility, and original visual
and audio feedback. It should define the planned first-release quiz catalogue
and its bounded production batches—not invent towns, characters, or boss fights.

For finite first-release content, decide the concrete content up front in
original design cards: for example named party members, bosses, locations,
quests, ability families, or boards/levels. For large or renewable content,
define the catalogue grammar, provenance, quotas, distributions, validation,
and bounded production batches instead of pretending one enormous document can
list every item. A design bible is complete only when later implementation
authors can tell what must be made, how much, why it belongs, and how it will
be verified.

## Acceptance criteria

- Every feature maps to a user outcome and journey.
- Normal, empty, invalid, permission-denied, offline, conflict, recovery, and deletion paths are specified where relevant.
- The first release provides one complete useful journey without deferred dependencies.
- Cross-target capability parity and intentional target-specific differences are documented.
- Each domain chapter defines its entities, rules, lifecycle, authoring inputs,
  dependencies, player/user outcomes, edge cases, and first-release boundary.
- The relationship map identifies cross-domain invariants and lifecycle
  boundaries. For example, an RPG quest links narrative and save state; an IDE
  edit links language analysis, workspace indexing, and version control; an OS
  permission links identity, process, storage, and user settings.
- Every game has a game-design bible that selects only relevant genre modules,
  maps stable `GAME-*` units to first-release journeys and implementation
  domains, and gives each selected module a bounded content/production plan.
- The game-bible JSON has non-empty `game_archetypes`, `selected_modules`, and
  `design_units`; every selected module owns at least one `GAME-*` design unit
  and every unit records its module, player outcome, production mode, and
  first-release scope. Rejected modules record why they are not part of this
  game, rather than being silently omitted.
- Finite content is represented by concrete original design cards; scalable
  content is represented by a catalogue rule, quantity/distribution, source or
  provenance policy, and bounded production batches. This applies equally to
  RPG content, trivia questions, puzzle packs, races, strategy units, and any
  other game-specific content.
- Games with the selected narrative module also have a narrative/content model
  mapping premise, player role, setting, characters, story units, progression,
  localisation/accessibility, and originality boundaries to those journeys.
