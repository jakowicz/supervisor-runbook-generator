## Objective

Create `projects/<project-slug>/planning/05-delivery-map.md`, an ordered inventory of
small, independently reviewable implementation tasks derived from F001–F004
and the target repository's actual structure. Partition shared foundations from
target-specific adapters, UI, input, distribution, and certification work.

Treat creative production as a dependency graph, not polish after coding.
Where applicable, include narrative/content packages and their validation,
original visual assets and integration, music/sound generation and integration,
accessibility equivalents, provenance review, and QA. Place these work items
early enough that gameplay, UI, asset loading, audio triggers, saves, and tests
are designed around the real content rather than placeholder-only assumptions.

For a game, create `planning/game-production-inventory.md` from the game-design
bible. It lists every selected `GAME-*` unit and, where relevant, its design
cards (characters, units, enemies, bosses, locations, quests, moves/abilities,
items, buildings, levels, UI surfaces, visual asset families, and audio cues),
with scope/quantity, dependency, original-design brief, owner, and verification
route. It is the bridge between design intent and bounded implementation work.
Create the matching machine-readable
`planning/game-production-inventory.json`. Each entry identifies its design
unit, selected module, content/design-card type, finite item or catalogue
batch, planned quantity, original brief, dependencies, asset/audio IDs,
implementation outcome, owner, and verification. Every selected module and
every `GAME-*` unit must have at least one inventory entry. A finite RPG roster
therefore names and describes its actual first-release party, bosses, towns,
quests, or items as appropriate; a football-trivia catalogue instead has
explicit category/difficulty/type quotas and small editorial batches with
source validation. Do not use vague entries such as “make game content.”

For a game, also create `projects/<project-slug>/game-design-runbooks/`, then
write `GD0001.md`: a bounded game-design-programme dispatcher. Register this as
the `game-design-runbooks` project collection. It inherits the project's
existing `PROJECT_BRIEF.md` and `INITIAL.md`; never create or duplicate an
`INITIAL.md` inside this collection.
GD0001 reads the discovery, identity, initial design bible, creative direction,
and production inventory; it writes `planning/game-design-manifest.json` and
creates at most ten `GB` bounded design-runbook writers, one `GC` catalogue
checkpoint, and one successor `GD` dispatcher when more work remains. Each
`GB` writer creates at most **five** focused `G` design runbooks. Those G files
create/review the detailed bibles required by the selected modules (not a fixed
RPG list), such as story/world/party/boss design for an RPG or question
bank/scoring/fairness design for trivia. `GC` validates G ownership, design-unit
coverage, dependency closure, output quality, and manifest consistency before a
later GD wave continues. GD dispatchers add further bounded waves until every
required design module and production entry has completed design evidence, then
create a final `GQ` design audit.
Each `GC` is a successful **checkpoint**, not the final manifest audit: it must
be accepted when it accurately records the coverage it inspected and either
(a) creates exactly one bounded `GD` successor containing every outstanding
evidence boundary, or (b) proves no successor is required and creates `GQ`.
An incomplete manifest is therefore a normal checkpoint finding, never a
reason to stop for user review after the successor has been created. Only the
later `GQ` task may accept the manifest itself.
Every generated GC must remain a normal runnable Supervisor runbook with
`## Objective`, `## Output list`, and `## Acceptance criteria`. Its audit is a
separate, durable file in `design-evidence/`; it must never rewrite its own
`.md` task file into a report, because that would make a safe retry impossible.
The final audit must update the canonical bible and inventory, run the
dedicated manifest completion check, and leave a completed manifest. The full
implementation-coverage validator runs later, after F012 creates its catalogue.
Do not generate B or R implementation runbooks until the G collection has
passed.

The manifest is a completion gate, not a prose report. Its required fields are
`status: accepted`, `final_audit` (`task_id: G...`, `status: accepted`), and a
`modules` array. Each selected module records `module`, `status: accepted`,
`design_output_paths`, `game_design_ids`, and `production_inventory_ids`.
It also records empty `pending_modules` and `blocked_modules` arrays. The final
audit may set these values only after it has checked all generated G evidence;
the Supervisor and `scripts/runbookgen validate` reject any other form. The
manifest module set must exactly match `02-game-design-bible.json`, and each
module must cover all of its canonical `GAME-*` design-unit IDs before F006 can
start.

Every generated `G0001`, `G0002`, … design task uses normal Supervisor task
metadata and declares `design_authoring_batch: GB0001` (or its actual GB
writer). G tasks are the actual game-design work; GB/GC/GD/GQ files are only
the scalable authoring, checking, dispatch, and audit layer that lets hundreds
of detailed G files be created without a single giant prompt.

## Acceptance criteria

- Each task has a bounded outcome, dependency set, verification strategy, and file/data ownership.
- Foundation, domain, features, accessibility, trust, operations, documentation, QA, and release work are included when in scope.
- Narrative/content, visual assets, audio, provenance, integration, and their
  accessibility/QA work are included as owned first-class tasks whenever the
  creative direction declares them in scope.
- Every game-design unit has a production-inventory entry and is either planned
  for the first release, explicitly deferred, or rejected with a reason.
- The JSON inventory proves every selected game module has concrete production
  work. It distinguishes finite, named creative content from scalable
  catalogues, and gives both a bounded, independently verifiable production
  plan.
- For a game, `game-design-runbooks/GD0001.md`, its child registration, and a
  game-design manifest exist. GB writers create no more than five G design
  tasks each; GC/GD/GQ provide the bounded quality, dispatch, and audit loop.
  Every generated GC has checkpoint acceptance criteria: verified coverage plus
  either a single explicit GD successor for remaining evidence or a final GQ
  audit when no remaining evidence exists. It must not demand an accepted
  manifest from an intermediate checkpoint. GC writes its audit to
  `design-evidence/` and never replaces its runnable task file.
  F006 cannot start until the G collection's final audit has accepted the
  selected modules, detailed bibles, and inventory.
- Browser-impacting tasks own unique future Playwright specification paths.
