## Objective

Create `projects/<project-slug>/planning/06-foundation-domain-contracts.md`.
Turn the foundation work from F005 into atomic implementation-contract records:
bootstrap, configuration, architecture seams, design tokens, data model,
persistence, identity, authorization, and test harnesses. This is an authoring
input, not an attempt to write every final implementation runbook in one task.

For a non-game product, `game-design-runbooks` is not required: record that it
is not applicable in the project handoff before this task is accepted.

For games, include the data and authoring seams required by the selected game
modules—not a generic game schema. This may mean content-card IDs and save
references for an RPG, or question identity, source attribution, answer
normalisation, category/difficulty distribution, anti-repeat state, and an
editorial validation harness for football trivia. Preserve the game-design
bible and production-inventory IDs all the way to runtime data and tests.

## Acceptance criteria

- Each record has a stable implementation ID, bounded outcome, dependencies,
  file/data ownership, verification, and acceptance evidence.
- For a game, the completed G-series manifest is a required input; every
  foundation/domain record preserves its relevant game-design and inventory
  IDs, rather than reinterpreting an unfinished high-level brief.
- Contracts identify shared and target-specific work without implementing later
  features early or substituting placeholders.
- The document is sufficient for a later batch author to create valid Supervisor
  runbooks without reinterpreting the brief.
