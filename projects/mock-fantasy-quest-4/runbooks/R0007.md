## Objective

Define a pure, ordered save-migration runner that accepts an untrusted saved
candidate, declares supported predecessor versions, and promotes only a fully
validated result. Failed or unsupported candidates retain their original bytes
and quarantine disposition; this contract does not select storage or repair
player data destructively.

## Dependencies

R0005 owns the versioned content and provenance schema boundary. R0006 owns
the local save, validation, current-pointer, known-good retention, and
quarantine protocol. Both are implementation dependencies. Retain GATE-0003 /
DEC-0003: a human decision is required for the supported migration window,
storage API, quota, and recovery policy before implementation relies on them.

## Ownership

- `src/core/save/{migrations,compatibility}/` migration registry and runner.
- `tests/core/save/fixtures/` predecessor, unsupported-version, and failed
  candidate fixtures.
- Migration registry data and the migration-runner API.

The runner owns only pure candidate transformations and their validation
boundary. R0006 retains persistence, pointer promotion, and quarantine record
ownership; adapters retain any future approved storage mechanism.

## Required behaviour

Represent every migration as an ordered pure transformation from one declared
schema version to its immediate successor. The runner must not read storage,
write storage, access a clock, mutate its input, or choose a current save. It
returns either one validated candidate with its resulting version or a typed
failure that leaves the supplied bytes and source version available to R0006's
quarantine path.

Before promotion, validate the complete transformed candidate using the save
schema, checksum/integrity process, and applicable invariants. Execute each
predecessor step once in ascending order; reject cycles, duplicate version
steps, gaps, unknown versions, and a result that cannot validate. Do not retry
by guessing, drop unknown fields silently, fabricate content, or repair data
in place. Only R0006's existing recovery protocol may retain or quarantine the
original candidate and promote a validated replacement.

## Web and PWA differences

Responsive web and installed PWA consume the same shared pure migration API.
Their eventual approved local-storage adapters may pass bytes into the runner,
but neither target gets a separate migration sequence. PWA cache and update
records never enter migration input and cannot be promoted as save data.

## Non-goals

Do not choose a storage driver, support window, retention policy, or recovery
policy; do not modify adapters, cache lifecycle, content packages, or current
pointers. Do not add export/import, cloud sync, accounts, remote services,
network transport, automatic destructive repair, UI, gameplay, product assets,
or audio.

## Asset assessment

`asset_impact` is `not_applicable`. The migration runner and synthetic
predecessor fixtures need no product asset. Do not create or reserve visual,
source, audio, icon, illustration, font, texture, sprite, map, or other
incidental asset; `asset_ids` and audio IDs remain blank.

## Verification

- Run deterministic fixtures for every declared predecessor and prove each
  takes its ordered path exactly once to a validated candidate.
- Prove unsupported versions, duplicate/gapped/cyclic registry definitions,
  thrown transformations, checksum failures, and invariant failures leave the
  original bytes intact and route to the typed failure/quarantine boundary.
- Prove the runner has no storage, network, clock, cache, pointer-promotion,
  or mutation dependency; web and PWA adapter fixtures use the same API.
- Before recording the B0005 checkpoint, load this runbook and compare its
  metadata, provenance, dependencies, requirement IDs, and ownership to the
  manifest. Stop on a mismatch; retain R0007 and never renumber or replace it.

## Evidence

Retain predecessor-chain outputs, input-byte equality assertions for every
failure, validation and quarantine-boundary results, purity/static dependency
checks, retained GATE-0003 / DEC-0003 evidence, and the successful loader and
manifest-comparison record.

## Acceptance criteria

- Every declared predecessor version migrates once through ordered pure steps
  and only a validated candidate can be returned for promotion.
- Unsupported or failed migrations preserve original candidate bytes for the
  existing quarantine/recovery protocol and never perform destructive repair.
- Migration support-window, storage, and recovery choices remain blocked by
  GATE-0003 / DEC-0003; no cache, remote, or asset scope is introduced.
