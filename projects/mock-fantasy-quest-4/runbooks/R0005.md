## Objective

Define the shared, versioned content-package schema, read-only registry, and
validator that reject malformed or internally inconsistent content before it
can be loaded for play. The contract validates structure and relationships;
it does not author a town, dungeon, dialogue, map, encounter, or other campaign
expression.

## Dependencies

R0001 provides the project boundary, R0003 provides deterministic fixtures,
and R0004 provides versioned campaign-state envelopes. They are implementation
dependencies, not authoring blockers. Retain GATE-0003 / DEC-0003: save storage
API, quota, support-window, and recovery policy decisions remain owned by the
local-save protocol. This content contract neither chooses nor writes a save or
cache implementation.

## Ownership

- `src/content/{schema,validator,registry}/`.
- `tests/content/validation.*` and deterministic content graph fixtures.
- `docs/content-authoring.md`.
- The versioned content-package, asset/provenance-manifest, and validator API
  contracts.

The content registry loads only a fully validated package and is read-only at
runtime. It does not own campaign state, save snapshots, preferences, browser
storage, PWA cache records, migrations, assets, or release packaging.

## Required behaviour

Model a package with stable package ID, semantic version, schema version,
default locale, scenes, exits, dialogues, quests, encounters, enemy and item
definitions, rewards, localisation, and an asset/provenance manifest. Validate
before registry publication: schema shape and bounded input, required fields,
unique stable IDs, locale-key and asset/provenance references, predicates,
scene/spawn/exit targets, reward/item/enemy references, duplicate reward IDs,
safe quest-item removal paths, and a reachable opening-to-ending path.

Validation must return typed diagnostics and must not partially register an
invalid package. Build-time content import runs through this validator; derived
bundles are never hand edited. Runtime discovery of a bad package stops the
affected route, retains existing campaign/save data, and offers title or retry
rather than mutating or replacing state.

Content compatibility is declared explicitly so the save/recovery owner can
compare a snapshot's content package/version without making the content
registry a persistence driver. Do not checkpoint, promote, overwrite,
quarantine, migrate, or delete a save here; those operations remain gated under
GATE-0003 and belong to R0006 and later R0007.

## Web and PWA differences

Web and PWA use the same shared validator, schema, and read-only registry. A
PWA cache is a delivery concern, not a content-validation result or save store;
neither target may bypass validation, write the active package at runtime, or
conflate cache failure with save recovery.

## Non-goals

Do not create authored campaign content, dialogue, maps, art, audio, sprites,
icons, localisation copy, release bundles, gameplay algorithms, UI flows,
browser/PWA cache lifecycle, save drivers, migrations, export/import, cloud
sync, accounts, network clients, or storage policy. Do not resolve GATE-0003
or GATE-0004; content quantities, locales, and detail remain unapproved.

## Asset assessment

`asset_impact` is `not_applicable`: this work defines schemas and validation
only. Do not create, reserve, source, or generate incidental visual, audio,
font, icon, illustration, texture, sprite, map, dialogue, or other product
asset; `asset_ids` and audio IDs remain blank. The schema may reserve fields for
later original assets and provenance review without assigning an asset.

## Verification

- Load a valid minimal package and prove publication succeeds only after all
  validation phases complete.
- Use one deterministic invalid fixture for each reference class: duplicate ID,
  missing locale or asset/provenance record, invalid predicate, unresolved
  scene/exit/reward/item/enemy reference, unsafe quest-item removal, and
  unreachable ending; prove no invalid fixture is registered.
- Traverse a valid fixture from opening scene to ending and prove required
  transitions and rewards resolve.
- Verify a runtime-invalid-package result retains the existing state/save and
  provides title/retry recovery without selecting a storage API.
- Before recording the B0004 checkpoint, validate the runbook loader parses
  this front matter, provenance is non-empty and maps to IMP-0005, dependencies
  match the manifest, owned paths are distinct from R0006, and every required
  section is present. Stop on any mismatch; never overwrite an R contract.

## Evidence

Retain validator output for the valid package and every rejected reference
class, reachability traversal output, registry non-publication assertions,
runtime title/retry recovery evidence, and the pre-checkpoint loader,
provenance, dependency, ownership, and required-section validation record.

## Acceptance criteria

- A valid minimal versioned package is the only kind of package the read-only
  registry can publish.
- Invalid IDs, references, predicates, localisation/provenance links, unsafe
  quest-item removal paths, and unreachable campaign graphs fail before play.
- Content/save compatibility is explicit while save, cache, migration, and
  storage decisions remain separate and GATE-0003 / DEC-0003 remains retained.
